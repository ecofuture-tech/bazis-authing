# bazis-authing 2.8.0

Requires Bazis 2.18 and bazis-users 2.9.

The Google sign-in in a browser starts with a POST: update the clients (see "Clients").

## Security

- **Login CSRF of the Google browser flow.** `GET /google-auth-init/?bazis_auth=<store
  token>` started a Google sign-in of any store, in any browser: an attacker sent a victim
  the link with the attacker's store; a victim who already consented to the app in Google
  returned without a prompt and signed the attacker's store in with the victim's account,
  and the attacker took the victim's session from `/auth/`. A one-time ticket alone would
  not stop it (the attacker gets one for the attacker's store), so the ticket is bound to
  the browser that asked for it:
  - `POST /google-auth-init/` with the store token as the bearer token answers
    `{"ticket", "url"}` and sets the cookie `__Host-bazis_google_init` with a random
    secret (HttpOnly, Secure, SameSite=Lax, `Path=/`, 60 seconds; the prefix makes sure
    that no other origin, a sibling subdomain or plain HTTP, set it). With
    `BAZIS_AUTH_COOKIE_SECURE` off the cookie is `bazis_google_init` without Secure. The
    ticket (one-time, in the cache, 60 seconds) holds the store and that secret. A new
    POST in the same browser replaces the cookie: the earlier ticket is refused.
  - `GET /google-auth-init/?ticket=<ticket>` (the `url` of the answer) uses the ticket once
    and only with the cookie of the same secret, drops the cookie and redirects to Google
    as before. A missing, used or expired ticket and a missing or wrong cookie answer 400
    alike; a store that is gone meanwhile answers 401.
  - The store token is in no URL of the flows any more.
  - Residual risks: with `BAZIS_AUTH_COOKIE_SECURE=false` the binding cookie has no
    prefix, and a sibling subdomain or a network attacker can plant it. The binding does
    not protect against a script on a same-site page that can send credentialed requests
    (an XSS on `app.site.com` can run the flow itself). The store cookie
    (`BAZIS_AUTH_COOKIE_NAME`) can be planted the same way: known, not changed in this
    release.

## Breaking changes

- The Google browser sign-in is a POST, then a GET of the window: the login action of the
  service `google` in `GET /auth/` has `method: POST` (it had `GET`); `url` is unchanged.
- `GET /google-auth-init/?bazis_auth=<store token>` answers 400 ("Missing ticket"). The
  setting `BAZIS_G_AUTH_INIT_LEGACY_GET` (default false; deprecated, removed in 2.9)
  accepts it again and makes the login action `GET` again, for the clients that are not
  updated yet (the login window of bazis-front opens the init URL with GET with the store
  token, and offers only the login actions with `GET` in a window). It re-opens the login
  CSRF: enable it only temporarily, until the clients are updated.
- The page that starts the sign-in must be same-site with the API (e.g. `app.site.com`
  and `api.site.com`, or the API behind the same origin): a browser does not store the
  SameSite=Lax cookie of a cross-site request. A cross-origin API also needs CORS with
  credentials (`BS_CSRF_TRUSTED_ORIGINS`).

## Clients

1. Take the login action with `code: google` (`method: POST`) from `GET /auth/`.
2. On the click, open the window at once (`window.open('', ...)`, or with `about:blank`):
   a browser blocks a window that a click does not open, and the URL is known only after
   the POST.
3. `POST url` with `Authorization: Bearer <store token>` and the cookies of the browser
   (`fetch(..., {credentials: 'include'})`; the answer sets the binding cookie). Set the
   location of the window to the `url` of the answer, a path of the API, like the `url` of
   the action. On an error (401: the store is gone, take a new one from `/auth/`), close
   the window.
4. Ask `GET /auth/` with the store token until the store is signed in, as before. A 400 in
   the window means the ticket expired or was used: start again.

## Changes

- `GET /auth/` raises its error answer as `JsonApiBazisException` with the store cookie as a
  `JsonApiCookie` of Bazis 2.18 (the attributes of the cookie are kept) instead of calling
  the exception handler of the application itself. The answer is unchanged.
- `AuthStore.as_cookie()`: the store cookie as a `JsonApiCookie`, for the error answers of
  own services; `response_set_cookie()` sets the same cookie.

## Deprecations

- Removed in 2.9, the next minor release (not 3.0 like the other deprecations: the
  setting re-opens a login CSRF): `BAZIS_G_AUTH_INIT_LEGACY_GET` and
  `GET /google-auth-init/?bazis_auth=<store token>`. The login window of bazis-front 0.4
  opens the init with GET and offers only GET actions, so with the setting off it shows no
  Google login until the bazis-front release with the POST flow.
