# bazis-authing 2.6.0

Requires Bazis 2.5.

Security hardening of the authorization store. The behavior of the sign-in flows changes:
check the clients (see "Upgrading").

## Changes

- **A store gives its session once.** `GET /auth/` with a signed-in store returns the
  session token and deletes the store (atomically: of concurrent requests only one gets the
  session). The next request with the store token gets the "not authorized" answer
  (HTTP 400, `UNAUTHORIZED`) with a new store, and the login endpoints answer 401 for it.
  Before, the store token gave a new session to anybody who had it until the store expired
  (`BAZIS_AUTH_COOKIE_LIFETIME`), and it travels in URLs and access logs. A failed login
  keeps the store: the client retries with it.
- **A signed-in store lives `BAZIS_AUTH_CLAIM_LIFETIME` seconds** (new setting, default
  60) instead of `BAZIS_AUTH_COOKIE_LIFETIME`: it only waits for `GET /auth/`.
- **`POST /logout/`** (the router of `bazis.contrib.authing.router`, route name
  `auth_logout`): deletes the stores of the request (bearer token, cookie, query parameter)
  and the `bazis_auth` cookie; 204, idempotent.
- **The store cookie** (`BAZIS_AUTH_COOKIE_NAME`) lives as long as the store instead of a
  year, and is HttpOnly, SameSite=Lax and Secure. New setting `BAZIS_AUTH_COOKIE_SECURE`
  (default true): set `BS_BAZIS_AUTH_COOKIE_SECURE=false` for development over plain
  HTTP. When `GET /auth/` gives the session of the store in the cookie, it deletes the
  cookie.
- **No store token in redirects.** `POST /password/` and `POST /google-auth-verify/` answer
  303 to `/auth/` without `?bazis_auth=<store token>`: the client follows the redirect with
  the same bearer token or the cookie, which the answer sets.
- **Google in a browser.** The OAuth state sent to Google is a one-time random value
  (mapped to the store in the cache), not the store token. `/google-auth-callback/` signs the
  store in and answers a page without tokens ("return to the application", it tries to
  close the window) instead of a redirect to `/auth/?bazis_auth=<store token>`: the client
  that holds the store token asks `GET /auth/` until the store is signed in or has an
  error. `/google-auth-init/?bazis_auth=<store token>` remains the only URL with the store
  token. The callback sets the store cookie only after authlib accepted the state and the
  sign-in succeeded: a callback URL with the state of another browser does not plant that
  store in the window.
- `AuthStore.redirect_to_auth()`: the answer of a login for own services (303 to `/auth/`
  with the cookie). `AuthStore.as_param` is deprecated (it puts the store token in a URL)
  and `AuthStore.cookie` is removed (a cookie without the attributes above).

## Known limitation

The GET `/google-auth-init/?bazis_auth=<store token>` allows a login CSRF: an attacker sends
a victim the link with the attacker's store; a victim who already consented to the app in
Google returns without a prompt and signs the attacker's store in with the victim's
account, and the attacker takes the session from `/auth/`. It is not fixed in this
release. Planned fix: a POST init with the store token as the bearer token that returns a
one-time ticket for the window URL, so that only the client holding the store can start a
Google sign-in for it.

## Upgrading

- Clients that read the session from `/auth/` more than once with the same store token
  (e.g. after a reload) must keep the session token instead, or start a new login.
- Clients that sent the store token only in the query string of the login request must
  follow the redirect with it as `Authorization: Bearer` (or keep the cookie).
- Clients of the Google browser flow that read the session from the window at
  `/auth/?bazis_auth=...` must ask `GET /auth/` with the store token themselves.
- Over plain HTTP, set `BS_BAZIS_AUTH_COOKIE_SECURE=false` if the clients use the cookie.
- Google logins in progress during the upgrade fail once (their state has the old format):
  the user signs in again.
